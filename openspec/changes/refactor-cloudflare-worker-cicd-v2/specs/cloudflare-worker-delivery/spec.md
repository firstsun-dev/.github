# Cloudflare Worker Delivery — v2 In-Place Refactor Delta Specification

**Scope:** the in-place, breaking refactor of the v2 shared workflow (`_cf-worker-v2.yml`) and its consumer contract. v1/v1.5 are unchanged and no new major (`v3`) is introduced. Requirements from `redesign-cloudflare-worker-cicd-v2` remain in force for eligible Native Previews except where the refactored job topology and migration/build contracts explicitly supersede them; the old v2 interface is not preserved.

## ADDED Requirements

### Requirement: The refactored v2 SHALL expose a minimal, independently gated delivery DAG

For each eligible Worker, the normal pipeline SHALL run six independent validation jobs in parallel (`Lint`, `Typecheck`, `Unit Tests`, `Integration Tests`, `Build Validation`, `E2E`), followed by a distinct `Migration` job, a single `Deploy` job, and an optional main-only `Release` job. A monorepo MAY prepend `Detect Changes` to select affected Workers. Each validation job SHALL have its own checkout, setup, environment import, logs, duration and conclusion, and SHALL NOT depend on another validation job. A combined CI job is NOT required.

#### Scenario: Validation jobs are configured
- **WHEN** an eligible trusted push starts
- **THEN** the six validation jobs SHALL be independently runnable without `needs` between them
- **AND** Migration SHALL wait for all configured validation results, treating a job skipped because its command is empty as satisfied and a configured job that skipped as a failure
- **AND** a failure or cancellation SHALL block the corresponding remote migration and deployment.

#### Scenario: E2E is intentionally disabled for an eligible Worker
- **WHEN** the E2E job is not required for that change or Worker
- **THEN** the skipped job SHALL not block Migration when all required validations succeeded
- **AND** failures SHALL not be disguised as an intentional skip.

#### Scenario: Deployment target is main
- **WHEN** production CI, required E2E, Migration, Deploy and smoke complete successfully
- **THEN** an applicable Release job MAY run
- **AND** it SHALL NOT precede required Production deployment verification.

#### Scenario: A Worker has no D1
- **WHEN** no remote D1 migrations apply
- **THEN** Migration SHALL be bypassed or complete a no-op
- **AND** that fact SHALL not prevent Deploy from running.

### Requirement: Validation and E2E SHALL build independently with their correct environments

Build Validation SHALL validate buildability with an explicitly documented target-aware configuration when needed. E2E SHALL be allowed to construct its own local/test build and services; Deploy SHALL independently build for its actual target. No normal delivery job SHALL require a GitHub Actions Build Artifact generated by another job.

#### Scenario: Local E2E and Production URLs differ
- **WHEN** E2E uses localhost/mock OAuth/test data and Production uses public URLs and live runtime bindings
- **THEN** E2E SHALL use its own test build/environment
- **AND** Deploy SHALL build anew from the same Git SHA using Production build variables and effective config
- **AND** no Build Artifact promotion SHALL be assumed.

#### Scenario: Preview and Production use different public variables
- **WHEN** the target changes between `preview` and `prod`
- **THEN** build-time URLs, analytics, noindex flags and relevant generated adapter bindings SHALL match that exact target
- **AND** CI build validation SHALL NOT count as proof that a different target configuration deploys correctly.

#### Scenario: Artifacts are over quota
- **WHEN** an optional failed-test report artifact cannot be uploaded
- **THEN** the test's original success/failure SHALL remain accurate
- **AND** deployment SHALL not depend on that artifact for code delivery
- **AND** optional failure evidence SHOULD have short retention (1–3 days by default).

### Requirement: Remote D1 migrations SHALL run as a separate, target-bound job

A D1-capable Worker SHALL run remote migration from a distinct reusable `Migration` job, never from its normal `Deploy` steps. Production and Preview SHALL apply the same repository-owned migration source to different, explicitly verified D1 databases; no centralized migration management service is required.

#### Scenario: Main push has pending migrations
- **WHEN** required CI/E2E pass for a trusted main push
- **THEN** Migration SHALL apply the pending migration files to the configured Production D1
- **AND** a successful Migration result SHALL gate the Production Deploy.

#### Scenario: Two feature branches share the Preview D1
- **WHEN** Preview-enabled branches use the same approved nonproduction D1
- **THEN** both SHALL apply pending files from the same project migration directory to that Preview D1
- **AND** already-applied migrations SHALL be skipped
- **AND** no separate per-branch D1 or migration SQL copy SHALL be created.

#### Scenario: A Preview D1 configuration is selected
- **WHEN** Migration targets a Native Preview
- **THEN** it SHALL verify the physical D1 equals the resource referenced by Wrangler `previews.d1_databases`
- **AND** it SHALL NOT assume the old named Wrangler `env.dev` is the Native Preview target
- **AND** it SHALL NOT modify Production D1.

#### Scenario: Applied migration name has conflicting content or order
- **WHEN** the branch migration source conflicts with applied nonproduction history
- **THEN** Migration SHALL fail with actionable diagnostics instead of silently treating incompatible content as safe
- **AND** Deploy SHALL not publish code dependent on the failed migration.

#### Scenario: Migration fails or nothing is pending
- **WHEN** Migration fails
- **THEN** Deploy SHALL not begin for that run
- **WHEN** no migration is pending
- **THEN** Migration SHALL complete successfully without D1 modification.

#### Scenario: Preview identity is validated before any remote migration
- **WHEN** a Preview-enabled branch push reaches Migration
- **THEN** the Preview name, ledger ownership (collision between normalized branch names), source binding policy, exact migration target and branch tip SHALL be validated before the first remote migration command
- **AND** a failed check, a deleted branch or a superseded commit SHALL leave the shared Preview D1 unmodified
- **AND** no custom migration command SHALL be able to bypass target validation.

#### Scenario: Pull-request validation
- **WHEN** the event is an untrusted PR or a PR-only validation path
- **THEN** remote D1 Migration SHALL not execute
- **AND** fork PR SHALL not receive migration credentials.

### Requirement: Mutation of a shared D1 SHALL be serialized across Migration and Deploy

For a Worker/target whose remote D1 is mutable, orchestration SHALL protect the complete Migration-to-Deploy interval against incompatible concurrent runs. Isolation SHALL be scoped by actual D1 ownership and Worker dependency, not merely by Branch URL. A lock applied separately to two job steps SHALL NOT be represented as atomic coverage of the interval between them.

#### Scenario: Two branches deploy concurrently against one Preview D1
- **WHEN** two eligible feature branches require migrations against the same shared Preview D1
- **THEN** the system SHALL prevent overlapping incompatible migration/deploy transactions
- **AND** a stale run SHALL not overwrite a more recent Preview of the same branch
- **AND** both independent branch Preview identities SHALL remain protected.

#### Scenario: Safe serialization cannot be proven
- **WHEN** the implementation cannot safely coordinate the complete interval or GitHub pending queue semantics
- **THEN** it SHALL conservatively serialize the affected target pipelines or fail closed
- **AND** CI and E2E within an executing pipeline SHALL still be scheduled in parallel.

#### Scenario: Production or cross-repository D1 access
- **WHEN** a D1 is shared with protected Dev or another repository
- **THEN** the owner SHALL explicitly approve the trust boundary and coordination design before enabling preview writes
- **AND** a same-repository concurrency key alone SHALL NOT be claimed to protect cross-repository access.

### Requirement: The refactored v2 SHALL use one target-aware Deploy job implementation

Production and Native Preview normal publishes SHALL share one reusable Deploy job and differ only through verified target-specific inputs/commands. Production permissions SHALL not be inferred from user-controlled `target` alone. Migration execution SHALL not be repeated in Deploy.

#### Scenario: Trusted main deployment
- **WHEN** the source is the allowed main ref and required gates succeed
- **THEN** Deploy SHALL use Production Environment/credentials, Production build inputs and versioned Worker publishing
- **AND** probe the Production URL and apply the approved recovery policy.

#### Scenario: Trusted feature push
- **WHEN** the source is an eligible non-main branch and required gates succeed
- **THEN** Deploy SHALL use Preview Environment/credentials, the stable branch identity and Native Preview publishing
- **AND** parse the actual Preview URL from Wrangler machine-readable output
- **AND** smoke that exact URL, not a guessed or constant Dev endpoint.

#### Scenario: Build or preflight fails before publish
- **WHEN** the target-specific build, environment resolution or binding preflight fails
- **THEN** Deploy SHALL not publish a new Worker version/Preview
- **AND** an existing branch Preview SHALL remain unchanged.

#### Scenario: Deploy did not actually deploy
- **WHEN** a Deploy job succeeds because the run was superseded, publishing was skipped, or smoke verification did not pass
- **THEN** it SHALL NOT report the deployment as verified
- **AND** Release SHALL require both a successful Deploy and an explicit verified-deployment output for the current SHA
- **AND** a missing smoke URL, an unapproved Cloudflare Access redirect, a failed SHA check or a rollback SHALL keep Release closed.

#### Scenario: Post-publish smoke fails
- **WHEN** the deployed endpoint does not pass required smoke tests
- **THEN** the deployment SHALL remain visibly failed
- **AND** use a tested code-recovery or actionable manual-recovery procedure
- **AND** SHALL NOT imply that Worker recovery rolled back D1 schema.

### Requirement: The caller SHALL own per-job environment variables and secrets boundaries

Consumers SHALL continue to supply application-specific configuration for each job, without a new mandatory centralized environment configuration generator. The workflow SHALL distinguish nonsecret CI/E2E inputs, target build inputs, remote D1 migration credentials and smoke credentials.

#### Scenario: E2E runs locally
- **WHEN** the app supplies `test_e2e_env`
- **THEN** only the E2E execution SHALL receive local/test URL and mock variables
- **AND** it SHALL not receive Production deployment tokens.

#### Scenario: Production and Preview builds
- **WHEN** a deploy target is `prod` or `preview`
- **THEN** Deploy SHALL import respectively `build_env_prod` or `build_env_preview`, validating each KEY=VALUE line
- **AND** it SHALL not expose runtime secrets through public `VITE_*`/`PUBLIC_*` values.

#### Scenario: Migration and smoke require credentials
- **WHEN** Migration accesses remote D1 or Smoke requires a test account
- **THEN** those credentials SHALL be scoped to the required job/step and trusted Environment
- **AND** neither shall be automatically inherited by unrelated CI/E2E steps or logged.

### Requirement: Monorepo execution SHALL follow affected-package and change-kind information

A monorepo SHALL use a lightweight Detect job for changed files and package dependencies, then run the same per-Worker CI/E2E/Migration/Deploy contract only where required. Root lockfile/workflow/shared test changes and unusable new-branch/force-push bases SHALL fail safe.

#### Scenario: ID-only source change
- **WHEN** only Heaven ID and dependencies change
- **THEN** ID SHALL receive required CI/E2E and its Preview/Production deployment
- **AND** unrelated Checkin/other Worker deployments SHALL be omitted.

#### Scenario: Shared package or Test Client dependency changes
- **WHEN** `heaven-core` or `heaven-id` dependencies affect multiple apps
- **THEN** every dependent Worker or test client SHALL be selected
- **AND** dependency relationships SHALL not be inferred exclusively from folder prefixes.

#### Scenario: E2E-only change
- **WHEN** only local E2E tests/helpers changed
- **THEN** the related E2E suites SHALL run
- **AND** unchanged Worker code SHALL not be automatically redeployed.

#### Scenario: First feature-branch push
- **WHEN** a new monorepo branch first pushes only one affected Worker
- **THEN** only that Worker SHALL create or update its Native Preview
- **AND** all other affected-worker selection rules remain enforced.

### Requirement: Existing Preview lifecycle and special deployment strategies SHALL be preserved

The refactored v2 SHALL preserve the previously shipped per-branch stable Native Preview, branch-identity collision checks, nonproduction resource preflight, fork trust boundary, protected Hybrid background-trigger testing, and documented Preview retention policy. This refactor SHALL NOT create one physical Preview D1/R2 per feature branch by default.

#### Scenario: Two Blog branches coexist
- **WHEN** two independent eligible Blog branches pass their gates
- **THEN** they SHALL retain independent stable URLs/code under `blog-preview`
- **AND** may share the approved `firstsun-blog-db-preview` and Preview R2
- **AND** no Preview SHALL write Production D1 or writable Production R2.

#### Scenario: Branch is deleted
- **WHEN** the source Branch delete event occurs
- **THEN** its GitHub Deployment ledger SHALL be retired for that identity
- **AND** the Native Preview SHALL be retained under the currently approved v2 owner policy
- **AND** no unrelated Worker Preview or shared resource SHALL be deleted.

#### Scenario: Hybrid and production-only exceptions
- **WHEN** an ID/Notification Hub Preview is published
- **THEN** it SHALL not assume Cron/Queue consumption executes on Native Preview or update persistent Dev
- **WHEN** an ANAS MCP non-main branch is tested
- **THEN** a public Cloudflare Access-bypassing Preview SHALL not be created.

### Requirement: The in-place breaking refactor SHALL not disturb pinned consumers before cutover

`_cf-worker-v2.yml` SHALL be refactored in place without a `v3` entrypoint or legacy-input adapters. `v1`/`v1.5.0` and every immutable `v2.x.y` tag SHALL remain unchanged, and the floating `@v2` tag SHALL NOT move until every consumer using it is ready and a reviewed cutover is made.

#### Scenario: Consumer has not migrated
- **WHEN** an existing consumer still pins v1, an immutable v2.x.y tag, or the floating `@v2` before cutover
- **THEN** the refactor on a feature branch SHALL not alter its deployed behavior.

#### Scenario: Pilot adoption
- **WHEN** Blog and Heaven ID migrate in separate reviewed PRs
- **THEN** both SHALL demonstrate correct E2E/test build versus target deploy build, distinct Migration Job, stable multi-branch Previews, smoke/recovery and applicable special checks
- **AND** the new immutable v2.x.y release and any move of floating `@v2` SHALL wait for verified pilot evidence.
