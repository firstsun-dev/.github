# Design

- **Separate post-deploy workflow, not an engine change.** `_cf-worker-v2.yml` already verifies and rolls back the Worker; adding portal state to it would couple every Worker consumer to MCP. The consumer calls `_mcp-post-deploy.yml` with `needs: pipeline` and passes `deploy_target`, `deploy_verified`, `rollback_result`.
- **Production only, structurally.** Every job is guarded by `deploy_target == production && deploy_verified == true && rollback_result == '' && push to refs/heads/main`. A PR Preview, Dev, an unverified or rolled-back delivery, and a skipped pipeline never reach the sync or the portal. `check-workflows.py` enforces the guard on every job.
- **Sequence.** upstream-smoke -> portal job (sync -> portal smoke -> dynamic portal smoke). A failed upstream smoke blocks the sync (a broken Worker is never published to a portal). Sync and portal smoke share one job so a single per-portal lock covers "sync + verify".
- **Concurrency.** Job-level group `mcp-portal-<portal_key>` with `cancel-in-progress: false` and `queue: max` (FIFO). Default GitHub semantics would drop an older pending run, silently skipping its sync; `queue: max` keeps every sync. Apps that share a portal pass the same `portal_key`.
- **Credentials.** `CF_ACCESS_CLIENT_ID/SECRET` are optional secrets, injected as `CF-Access-Client-Id/-Secret` only by `mcp-smoke.mjs`, masked with `::add-mask::`, redacted from every diagnostic. One without the other fails (never a silent anonymous run). The anonymous-refusal probe proves no Bypass policy.
- **Dynamic portal.** URL gets `optimize_context=search_and_execute`; expects `portal_query_tools` + `portal_execute` (Cloudflare reference table; the changelog says `query`/`execute`, so the pair is the `portal_dynamic_tools` input). Upstream tools are discovered with `portal_query_tools` and called through `portal_execute`; argument keys are mapped from each tool's `inputSchema` and fail loudly when they cannot be.
- **Sync result.** Pass only on `success: true` and `result.status == ready`; `waiting` and `retryable` errors are retried (bounded); `stale`, `error`, HTTP errors and malformed answers fail with the API's diagnostics.
- **OAuth-user vs service-token.** This workflow only runs service-token smoke and labels its summary so. User-OAuth tests (Diet Manager) are a separate consumer job/check.
